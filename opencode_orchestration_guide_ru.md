# Оркестрация OpenCode в существующем репозитории

Этот гайд настраивает небольшой, проверяемый процесс работы с OpenCode. Он
использует встроенные primary-агенты OpenCode, `Task` для subagents, явный
task-spec и технические permissions. Цель -- получить минимальное проверенное
изменение, не передавая между этапами всю историю чата.

## 1. Модель OpenCode

- `AGENTS.md` содержит устойчивые знания и ограничения проекта.
- `skills` содержат переиспользуемую методику, загружаемую через tool `skill`.
- primary-агент ведёт задачу и может вызывать subagents через tool `Task`.
- subagents исследуют или проверяют ограниченную часть работы.
- `commands` запускают повторяемые сценарии с явными аргументами.
- task-spec в `.opencode/tasks/<task-id>.md` хранит переносимое состояние одной
  задачи.

OpenCode уже включает primary-агенты `plan` и `build`, а также subagents
`explore` и `general`. Не создавайте кастомного агента, если встроенный
решает задачу. В этой конфигурации добавлены только роли, которых нет во
встроенном наборе: исследователь, adversarial reviewer и verifier.

`@agent` предназначен для явного вызова subagent. Primary-агенты переключаются
в интерфейсе OpenCode или выбираются через `opencode --agent <name>`; не
описывайте вызов primary-агента через `@`.

## 2. Постоянные инструкции

Запустите OpenCode из корня репозитория:

```bash
opencode
```

В `AGENTS.md` помещайте только информацию, применимую к большинству задач:

- назначение и структуру проекта;
- стек и реальные команды проверки;
- архитектурные границы;
- опасные операции, требующие остановки;
- правила работы с незакоммиченными изменениями и секретами.

Не помещайте туда историю задачи, длинные логи, полную документацию и правила
конкретного workflow. Для документации подключайте только короткие и актуальные
файлы в `opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["docs/architecture.md"]
}
```

В текущем репозитории `AGENTS.md` уже задаёт Python 3.13, `uv` и необходимые
команды проверки.

## 3. Структура файлов

```text
.opencode/
├── agents/
│   ├── orchestrator.md
│   ├── researcher.md
│   ├── reviewer.md
│   └── verifier.md
├── commands/
│   ├── prepare.md
│   ├── review-plan.md
│   ├── implement.md
│   ├── verify.md
│   ├── review-diff.md
│   └── task-status.md
├── skills/
│   └── engineering-workflow/
│       └── SKILL.md
└── tasks/
    ├── README.md
    └── TEMPLATE.md
```

`tasks/` игнорируется Git, потому что хранит временное состояние работы. Если
task-spec нужен как аудитный артефакт, уберите это правило из `.gitignore` и
договоритесь о схеме имён и владельцах файлов.

## 4. Роли агентов

### Orchestrator

`orchestrator` -- основной primary-агент. Он классифицирует задачу, создаёт
task-spec, вызывает ограниченных subagents через `Task`, запрашивает решение
человека при необходимости, реализует задачу и фиксирует результаты проверки.

Его `permission.task` разрешает только известные роли. Это исключает случайный
вызов произвольных subagents. Встроенные `plan` и `build` остаются хорошим
вариантом для задач, не требующих этого workflow.

### Researcher

`researcher` -- скрытый read-only subagent. Он ищет только минимально нужные
точки входа, аналоги и тесты. Результат содержит подтверждённые факты,
предположения, план, критерии приёмки и команды проверки. Он не меняет файлы.

### Reviewer

`reviewer` -- скрытый read-only subagent. Он проверяет task-spec или diff и
возвращает только подтверждённые замечания `BLOCKER`, `MAJOR` или `MINOR`.
Каждое существенное замечание обязано содержать repository evidence, последствие
и минимальную коррекцию. Отсутствие BLOCKER и MAJOR означает `APPROVED`.

### Verifier

`verifier` не исправляет код и не переписывает спецификацию. Он запускает только
указанные проверки, сопоставляет результаты с acceptance criteria и сообщает
фактический статус. Для очень простой задачи эту роль может выполнить основной
агент.

### Security review

Отдельный security-reviewer добавляйте только после появления повторяемого
потока работ. Второй reviewer оправдан для authentication/authorization,
платежей, миграций, секретов, публичных API или необратимых операций.

## 5. Permissions -- техническая граница

Инструкция в prompt не является защитой. `edit: deny` запрещает инструменты
редактирования, но не запрещает изменение файлов через произвольный `bash`.
Поэтому у researcher и reviewer произвольный `bash` запрещён; разрешены только
безопасные команды чтения состояния Git. Поиск и чтение выполняются встроенными
`glob`, `grep`, `read` и, когда доступен, `lsp`.

`steps` ограничивает число agentic-итераций, но не является лимитом токенов,
стоимости или времени. Retry policy в skill также является дисциплиной процесса,
а не технической гарантией.

`ask` показывает пользователю запрос на действие. Запуск с `--auto` одобряет
только запросы, которые не были явно запрещены. Не используйте `--auto`, пока
не заданы явные `deny` для опасных операций.

## 6. Task-spec

Для средней и сложной задачи сначала создайте отдельный файл:

```text
.opencode/tasks/<task-id>.md
```

Пример запуска:

```text
/prepare resend-confirmation Добавить повторную отправку письма подтверждения.
```

Task-spec должен содержать:

- `task_id`, `status`, `risk` и цель;
- ограничения и repository evidence;
- подтверждённые факты и предположения;
- запланированные изменения и acceptance criteria;
- команды проверки;
- замечания review;
- изменённые файлы, отклонения и остаточные риски.

Допустимые статусы:

```text
draft -> researched -> reviewed -> approved -> implementing -> verification -> done
                                                              -> blocked
```

Эта схема -- соглашение процесса. Команда и агент должны читать статус до
перехода, но OpenCode сам по себе не запрещает запуск команды вне этого порядка.

## 7. Маршруты задач

### Простая задача

Примеры: локальное переименование, текст, простой тест, очевидный изолированный
bugfix.

```text
build -> focused checks -> diff inspection
```

Не создавайте task-spec и не вызывайте reviewer без реального риска.

### Обычная задача

Примеры: endpoint, интеграция с существующим модулем, бизнес-функция в
нескольких файлах.

```text
orchestrator -> researcher via Task -> task-spec -> implement -> verifier
```

Проверяйте итоговый diff reviewer-ом, если затронуты несколько контрактов или
есть неопределённость. Не проводите review плана по умолчанию.

### Рискованная задача

Примеры: миграция данных, публичный контракт, авторизация, платёж,
конкурентность, необратимая операция.

```text
orchestrator -> researcher -> reviewer(plan) -> human gate -> implement
             -> reviewer(diff) -> verifier
```

Human gate должен быть явным: основной агент вызывает `question`, перечисляет
риски и ждёт ответа. Это ручное решение, не автоматическая гарантия.

## 8. Команды

Все команды используют явный `<task-id>`, поэтому subagent получает task-spec
по пути, а не полагается на историю текущего чата.

```text
/prepare <task-id> <task description>
/review-plan <task-id>
/implement <task-id>
/verify <task-id>
/review-diff <task-id>
/task-status <task-id>
```

`/prepare` создаёт task-spec из `TEMPLATE.md` и вызывает researcher. Если файл
уже существует, команда должна остановиться и попросить выбрать другое имя или
явно продолжить существующую задачу. Это предотвращает случайную перезапись.

`/review-plan`, `/verify` и `/review-diff` обязаны читать файл по переданному
пути. Они не используют формулировку "plan supplied in the current context".

## 9. Реальные проверки этого репозитория

Начинайте с узкой проверки, затем расширяйте её при необходимости:

```bash
uv run ruff check .
uv run --package csa-shared-kernel pytest
uv run --package csa-domain pytest -m "not integration"
uv run --package csa-worker pytest -m "not integration"
```

Для focused test добавьте путь или `-k <expression>` к соответствующей команде
пакета. Не заявляйте успешный результат, пока команда не была выполнена.

`pre-commit run --all-files` может форматировать и исправлять файлы, поэтому он
не является read-only проверкой.

## 10. Контроль контекста и стоимости

Передавайте между стадиями только task-spec, status, acceptance criteria,
repository evidence, открытые блокеры и результаты команд. Не переносите весь
чат, скрытые рассуждения, полные логи и отвергнутые варианты.

Для сложной задачи primary-агент может распараллелить независимые исследования
через `Task`: например, одно для кода, одно для тестов и одно для внешнего
контракта. Не запускайте параллельные subagents, которые редактируют одни и те
же файлы.

Используйте `todowrite` в primary-агенте для оперативных шагов. Task-spec --
долговечный артефакт конкретной задачи, а todo-list -- рабочее состояние сессии.

Повышайте модель или добавляйте reviewer только при фактах: повторной неудаче
ремонта, конфликте архитектурных подходов, публичном контракте, миграции,
сложной конкурентности или высокой цене ошибки. Не делайте это ради ещё одного
мнения.

## 11. Возобновление работы и автоматизация

Для продолжения сохранённой сессии используйте:

```bash
opencode --continue
```

Для альтернативного подхода без смешивания контекста:

```bash
opencode --continue --fork
```

Для воспроизводимого неинтерактивного запуска доступен `opencode run --agent`.
Автоматический `/solve` не добавляйте, пока workflow не прошёл 5--10 реальных
задач. Сначала измерьте лишние чтения, качество планов, шум reviewer-а, нужные
команды проверки, частые блокеры и реальную доступность моделей.

Если потом потребуется настоящий автоматический gate по статусу task-spec,
реализуйте его plugin, custom tool или внешним скриптом. Один только prompt не
может сделать gate обязательным.

## 12. Smoke test

После добавления конфигурации проверьте:

1. `/prepare demo-task ...` создаёт task-spec, но не меняет исходный код.
2. Researcher и reviewer не имеют доступа к edit и произвольному bash.
3. Orchestrator может вызвать только разрешённые subagents через `Task`.
4. `/review-plan demo-task` и `/review-diff demo-task` читают task-spec явно.
5. `/verify demo-task` запускает только реальные команды из task-spec.
6. Неизвестная модель даёт понятную ошибку; идентификаторы моделей проверяются
   в конкретной установке OpenCode перед фиксацией во frontmatter.
7. Доступ к `.env`, внешним директориям, миграциям и destructive-командам
   требует отдельного решения пользователя.

## 13. Антипаттерны

- Вызов primary-агента через `@`.
- Reviewer без явного task-spec или acceptance criteria.
- Read-only агент с `bash: ask` и разрешением на произвольные команды.
- Один общий `current.md` для параллельных задач.
- Копирование полной истории чата между агентами.
- Два reviewer-а для обычной безопасной задачи.
- Объявление prompt-инструкции технической защитой.
- Заявление об успешных тестах без запуска команд.
- Применение непроверенного model identifier.
- Создание `/solve` до проверки ручного процесса.

Главный принцип: не собирайте совет моделей. Стройте короткий конвейер с
конкретными ролями, явным состоянием, техническими границами и проверяемыми
условиями перехода.
